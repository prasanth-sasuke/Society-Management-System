# Deployment

## Production architecture

```
Android app (APK) ─┐
                   ├─► https://society-operations-suite.onrender.com  (Render web service, free plan)
Browser ───────────┘        Node.js API  +  built React app (web/dist) on the same origin
                                 │ DATABASE_URL (pooled)
                                 ▼
                            Neon PostgreSQL 18 (cloud)
```

- **Render** builds and runs the Node server. The same process serves `/api/*` and the built web app,
  so the browser needs no CORS setup and no separate web host.
- **Neon** hosts PostgreSQL. The app uses the **pooled** URL (`DATABASE_URL`, host contains `-pooler`);
  migrations use the **direct** URL (`DIRECT_URL`).
- **Expo EAS** builds the Android app in the cloud. The production API URL is baked into the app at build time.

## 1. Database (Neon)

One-time setup (already done for the current deployment):

1. Create a project at https://console.neon.tech.
2. Neon dashboard → **Connect**:
   - Copy the **pooled** connection string → `DATABASE_URL`.
   - Turn pooling off and copy the **direct** string → `DIRECT_URL`.
   - Both must end with `sslmode=require`.
3. Save them locally in the gitignored `.env.cloud` (copy `.env.cloud.example`). Add
   `SUPERADMIN_EMAIL` / `SUPERADMIN_PASSWORD` there if they should differ from `.env`.
4. Deploy the Render service (section 2). Its start script creates all tables with `prisma migrate deploy`.
5. Create the first login on the still-empty cloud database, then check it:
   ```bash
   cd server
   npm run prisma:seed:cloud     # refuses if the database already has a society
   npm run verify:cloud          # prints counts and migrations applied (URLs are redacted)
   ```

In normal operation you never run migrations by hand: Render applies pending ones on every start.

`npm run migrate:cloud` copies the **local** database into Neon. It was used once to move
data; it refuses to overwrite a cloud database that already has flats unless `FORCE=1` is set.
Do not use it on a live production database.

## 2. Web + API (Render)

The service is described in `render.yaml` (Blueprint):

| Setting | Value |
|---|---|
| Build command | `bash scripts/production-build.sh` — `npm ci` + `prisma generate` for the server, `npm ci` + `vite build` for the web app |
| Start command | `bash scripts/production-start.sh` — `prisma migrate deploy` using `DIRECT_URL`, then `node server/src/index.js` |
| Health check | `/api/health` |
| Node | 22 (`NODE_VERSION`) |

### First deployment

1. Push the repository to GitHub.
2. Render dashboard → **New → Blueprint** → select the repository. Render reads `render.yaml`.
3. When prompted, paste `DATABASE_URL` (pooled) and `DIRECT_URL` (direct) from `.env.cloud`.
   `JWT_SECRET` is generated by Render automatically; `NODE_ENV=production` and `JWT_EXPIRES_IN=12h` come from the blueprint.
4. Wait for the deploy, then open `https://<service>.onrender.com/api/health` → `"db":"up"`.

### Deploying a change

```bash
git add -A
git commit -m "Describe the change"
git push origin main
```

Render auto-deploys `main`: it builds, runs pending migrations, then switches traffic.
Watch progress under the service's **Events** and **Logs** tabs.

Database schema changes: create the migration locally with `npx prisma migrate dev --name <change>`,
commit the new folder under `server/prisma/migrations/`, push. The start script applies it to Neon.
Take a backup first (`npm run backup:cloud`) when a migration changes or drops existing columns.

### Free plan behaviour

The free Render service sleeps after about 15 minutes without traffic. The next request
wakes it up, which can take up to a minute; the web and mobile apps simply wait. A paid
instance (or an external uptime ping) removes the delay.

### Changing secrets

- **Rotate `JWT_SECRET`**: Render → service → Environment → edit → Save. Everyone is signed out.
- **Rotate the Neon password**: Neon → Roles → reset password, then update `DATABASE_URL` / `DIRECT_URL`
  in Render and in your local `.env.cloud`.

## 3. Android app builds (EAS)

Project: `@lakshmiprasanth/society-operations-suite`, package `com.societyops.suite`.
Profiles are in `mobile/eas.json`; both set `EXPO_PUBLIC_API_URL` to the Render URL.
The signing keystore is stored by Expo (do not lose access to the Expo account).

```bash
cd mobile
npm install -g eas-cli          # once
eas login                       # once (Expo account)

# Installable APK for testing / sharing (internal distribution)
eas build -p android --profile preview

# Play Store bundle (.aab), version code auto-increments
eas build -p android --profile production
```

The command prints a build page link; when it finishes, the page shows the download link for the APK/AAB.
All builds are also listed at https://expo.dev under the project's **Builds**.

Rebuild the app whenever mobile code, icons, `app.json` or the API URL change. Server-only
changes do **not** need a new app build — the app always talks to the live API.

- **Install the APK**: open the download link on the phone → allow "Install unknown apps" for the browser → install.
- **Play Store**: needs a Google Play Console account (one-time US$25). Upload the `.aab` from the production profile
  (`eas submit -p android` can upload it once a service-account key is configured).

### App size

`mobile/app.json` configures `expo-build-properties` to keep the Android download small:

- `buildArchs: ["armeabi-v7a", "arm64-v8a"]` — native code only for real phone processors (64-bit and older 32-bit ARM).
  The emulator-only `x86` / `x86_64` copies are left out. Add `"x86_64"` back only if you need to install the APK on an Android emulator.
- `enableMinifyInReleaseBuilds` + `enableShrinkResourcesInReleaseBuilds` — R8 removes unused Java code and resources.

Play Store `.aab` builds are smaller still for users: Google delivers only the parts each phone needs.

## 4. iOS app builds (EAS)

The app is configured for iPhone (`ios.bundleIdentifier` = `com.societyops.suite`, iPhone only, and
`ITSAppUsesNonExemptEncryption=false` because it only uses standard HTTPS). No Mac is needed; EAS builds in the cloud
and manages Apple certificates.

1. Join the **Apple Developer Program** (US$99/year) at https://developer.apple.com/programs/ with an Apple ID that has
   two-factor authentication. Wait for the approval email.
2. Build:
   ```bash
   cd mobile
   eas build -p ios --profile production     # sign in with the Apple ID when asked; let EAS create certificates
   ```
3. Distribute:
   - **TestFlight (recommended)** — `eas submit -p ios --latest` uploads the build to App Store Connect
     (the first time, EAS creates the app record). In App Store Connect → TestFlight, add testers by email or create a
     public link. External testers need a short Apple beta review of the first build. Testers install the **TestFlight** app, then this app.
   - **Ad hoc (up to 100 registered iPhones)** — register each phone with `eas device:create` (it gives a link to open on the iPhone),
     then `eas build -p ios --profile preview` and open the install link on a registered phone.
   - **App Store** — after TestFlight, submit for review in App Store Connect. Provide screenshots, a privacy policy URL,
     and a demo login for Apple's reviewer (create a dedicated reviewer account, not the superadmin).

Before the Apple account exists you can still try the app on an iPhone with **Expo Go** (App Store) and `npx expo start`,
exactly like on Android (see [LOCAL-SETUP.md](LOCAL-SETUP.md)).

## 5. Backups and restore

Neon's free plan keeps only a short restore window, so take your own backups.

### Create a backup

```bash
cd server
npm run backup:cloud
```

- Reads the Neon URL from `.env.cloud` (never printed).
- Uses the local `pg_dump` if its major version matches the Neon server; otherwise runs `pg_dump`
  from the matching `postgres:<version>-alpine` Docker image.
- Writes `dumps/neon-YYYYMMDD-HHMM.dump` (custom format), checks it with `pg_restore --list`,
  and keeps the newest 14 (`BACKUP_KEEP=30 npm run backup:cloud` to keep more).
- `dumps/` is gitignored. Copy important dumps somewhere off the laptop (for example an encrypted drive or cloud storage).

Suggested schedule — weekly with cron (`crontab -e`):

```cron
0 9 * * 1  cd "/home/sasuke/prasanth/project/Free launching/social management/server" && /home/sasuke/.nvm/versions/node/v22.23.2/bin/node scripts/backup-cloud.js >> ../dumps/backup.log 2>&1
```

### Test a backup (safe, throwaway database)

```bash
docker run -d --rm --name restore-test -e POSTGRES_PASSWORD=test -p 55432:5432 postgres:18-alpine
sleep 5
docker run --rm --network host -v "$PWD/../dumps:/backup" postgres:18-alpine \
  pg_restore --no-owner --no-privileges -d "postgresql://postgres:test@127.0.0.1:55432/postgres" \
  /backup/neon-YYYYMMDD-HHMM.dump
docker exec restore-test psql -U postgres -c "select count(*) from users;"
docker stop restore-test
```

### Restore into Neon (disaster recovery)

Restoring replaces production data. Prefer restoring into a **new Neon branch** first
(Neon → Branches → Create branch), check it, then point Render at it or restore into main.

```bash
# TARGET_URL = direct (non-pooler) URL of the branch/database to restore into
docker run --rm --network host -e TARGET_URL -v "$PWD/../dumps:/backup" postgres:18-alpine \
  sh -c 'pg_restore --clean --if-exists --no-owner --no-privileges -d "$TARGET_URL" /backup/neon-YYYYMMDD-HHMM.dump'
```

Set `TARGET_URL` in the shell first (`read -rs TARGET_URL; export TARGET_URL`) so the password does not end up in shell history.
